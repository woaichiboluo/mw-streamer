Synthetic H.264 NVDEC decoded-picture-buffer regression fixture.
224x100, High profile, level 3.1, 24 fps, 24 frames, video only, 16,783 bytes.
Generated from FFmpeg's testsrc2 source; no third-party recording is included.
SPS declares max_num_ref_frames=16, max_dec_frame_buffering=16, and
max_num_reorder_frames=2 (verified using the trace_headers bitstream filter).

Generated using FFmpeg 8.1.3:
ffmpeg -f lavfi -i testsrc2=size=224x100:rate=24 -frames:v 24 -pix_fmt yuv420p -c:v libx264 -preset medium -threads 2 -profile:v high -level:v 3.1 -x264-params ref=16:bframes=3:b-adapt=0:b-pyramid=normal:keyint=24:min-keyint=24:scenecut=0 -movflags +faststart h264_cuda_dpb.mp4

On the Windows/NVIDIA regression host, automatic decoder threads over-allocate
NVDEC surfaces. The following independent reproduction logs
cuvidCreateDecoder CUDA_ERROR_INVALID_VALUE and 36 decode surfaces, followed by
zero output frames and a nonzero exit code. The CLI's additional frame pool
makes this slightly larger than the 34-surface failure originally found in
Input on the Unified Streaming HLS sample. Requiring hwdownload prevents the
CLI's software fallback from falsely passing the hardware regression.

ffmpeg -hwaccel cuda -hwaccel_output_format cuda -threads 0 -i h264_cuda_dpb.mp4 -vf hwdownload,format=nv12 -f null -

Replacing -threads 0 with -threads 2 decodes all 24 frames on CUDA, downloads
them successfully, and exits zero. The test validates CUDA frame buffers,
timestamps/counts against independent software decoding, Flush, and retained
GPU frames after decoder recreation; it does not inspect the thread setting.
